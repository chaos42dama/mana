# Architect rationale 模板（design.md 八段骨架）

`/mana architect` 每次合成的 design package（`.mana/<design-id>/design.md`）按以下八段写，一页以内。括号内的说明是写作要求，交付时替换为实际内容。各候选 lane 写 `candidates/<n>.md` 时用同一骨架，`Synthesis decision` 一段留空，由合成阶段填写。

## Problem

（这一段要回答：解决什么问题，现有系统或约束里是什么让形状变得不显然。接地阶段发现的硬约束——必须兼容的既有类型、不能破坏的调用方、跨边界的 invariant——在这里点名，让读者看到与设计者相同的约束。常见写错：把需求复述一遍当问题；漏掉接地发现的硬约束，导致 Shape 段的决策没有锚。greenfield 跳过接地阶段的，在此写明跳过理由。）

## Usage（caller 的视角）

（这一段要回答：调用方看到什么。先写 usage 再推类型——先给出消费者会读的 README 式用法和两三个真实调用点：import 什么、调用什么、返回什么；Shape 段的类型草图由此推导，两者不一致时改草图、不改 usage——caller 的体验就是 spec。常见写错：先写类型再编一个配合它的用法示例，用实现上的顺手反推公共面。）

## Shape

（这一段要回答：推荐的架构长什么样。数据结构优先，然后写数据如何流经各签名，点名承重决策：哪些 invariant 编进了类型、校验放在哪、系统刻意不做什么。显式评判接口深度——公开面藏起了什么复杂度、什么仍暴露给 caller、为什么公共面不再需要更大。常见写错：罗列模块清单而不给数据流；拿「以后再加个缓存/索引」当结构答案——那说明结构本身错了。）

## Synthesis decision

（这一段由交叉评审阶段填写：基底选了哪个候选、为什么；从其余候选各吸收了什么；否决了什么、为什么。常见写错：只写「选了候选 1」——没有吸收与否决记录的合成等于没做交叉评审；单候选直接通过不合规。）

## Tradeoffs accepted

（这一段要回答：选定形状接受了哪些代价。每条一个取舍，形式「我们接受 X 换取 Y」；把未来读者可能误当疏忽的点都写出来，包括看起来像过早优化或过早简化的点。常见写错：只列优点；把默认值当决策——写不出另一面就不算 tradeoff。）

## Alternatives considered

（必填。这一段要回答：还考虑过哪些别的整体形状、为什么输了。至少一个具体替代形状 + 一句败因；按接口深度评判，不只看实现是否简单——写清它暴露给 caller 什么复杂度、藏起了什么。设计空间确有竞争者时给两三个；约束唯一解时给一个，措辞为「这是唯一可行形状，因为…」；避免罗列同一形状的变体。本段写被选形状考虑并否决的设计替代，不是复述其它候选 lane。常见写错：整段缺失——缺本段的 rationale 判不合规；拿「其它方案太复杂」这类不可证伪的话当败因。）

## Open questions and risks

（这一段要回答：哪些事需要 CTO/用户裁决、哪些风险要在实现前亮出来。以问题句式写，人的回答即结论，而不是事后评论。常见写错：把已经决策的事再列一遍凑数；把风险写成断言——「这样不行」不如「若 X 成立，这里会怎样？」）

## Next implementation step

（这一段要回答：对着这份 sketch 落地的第一步是什么，一句话——合成签收后立刻会动手写的那件事。常见写错：写成里程碑计划；或把实现写进本入口——实现归 `/mana run`，本段只指方向，不写实现代码。）
