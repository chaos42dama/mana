# why epistemics：证据分级与措辞规则

`/mana why` 合成环节（synthesizer）的证据分级框架。动机证据天生是**历史性、残缺、可能有偏**的：代码不携带自己的动机——它是什么读得出来，为什么存在读不出来；“为什么”活在 commit、PR、Issue、文档与对话里，而它们不完整、有偏、常常整体缺失。装作读到了，产出的只是听起来自信的猜测，而用户会照着猜测行动。所以每条结论必须显式定级，不许 factual 与 speculation 一个口径输出。

## 证据四档

最终输出里的**每一条结论**必须落在四档之一；档位决定结论的措辞与走向。

### direct —— 有人白纸黑字写过为什么

显式、有文本出处的引用，直接回答了问题。不是「代码做了 X，所以作者想必想要 X」——那是推断。必须是作者实际**写下**的话：

- PR 正文：「修的是用户有 >1000 条时无法分页」
- Issue：「加这个是因为客户 Acme 的安全评审要求」
- 代码注释：「// clamp 到 100，上游 API 拒绝更大的值」
- 设计文档：「选 A 不选 B，因为需要跨重启持久化」

**措辞**：直接、确定：「这段代码存在是因为 X，出处见〈引文〉」；引文紧邻结论，可点击/可回溯。

### supported —— 有指向性证据但没直说

多条旁证汇聚、无单一来源明说，但跨来源的模式使结论很可能成立：

- PR 标题写「improve performance」、Issue 打了 `perf` 标、前后多个 commit 都碰同一条热路径
- 改动同期新增的多个测试都在压同一个边界
- 作者同期其他 PR 正文里反复出现同一背景事件

**措辞**：笃定但明示推导：「证据强烈指向 X：〈逐条点名〉」。引多个出处。

### inference —— 推断，必须写出推断链

合理读出上下文、但没有任何文本直接支持；读者必须能看出这是**你的解读**，不是记录里的事实：

- PR 没写为什么，但事发当时线上正在报错（时间线对得上）、且当天即合并——很可能是紧急 hotfix
- 函数名暗示重试、次数是 3、与全库「3 次」惯例一致

**措辞**：一律打折限定：「看上去」「很可能」「暗示」「与…一致」「一种读法是」，且推断链要写明白：「鉴于 A 与 B，C 很可能成立，因为 D」。

### unknown —— 查不到，明确说查不到

查了、没查到。这是**有效且重要**的结局，不是失败。

**措辞**：说了查过哪里以及没查到什么，具体到可复现：「用关键词 A、B 检索了 Issue / 翻了该文件自 2023 年以来的 N 个 PR / grep 了该阈值字面量，均未找到 rationale」。「查不到」三个字单独出现没有信息量，必须补上查证范围。

## 措辞规则（档位与词的对应）

**高确定性词**——用了就必须紧邻出处（direct/supported 专用，禁止配 inference）：

- 「因为」「缘由是」——隐含因果+证据
- 「为…而设计」——声称作者意图
- 「修复了/解决了」——声称改动达成了目标
- 「团队决定」——声称有过一次集体决策

**低确定性词**——inference 专用：「看上去」「似乎」「很可能」「暗示」「一种解释是」。另外「而已/就是为了 X 而已」这类一言带过的口吻通常在掩盖不确定性，禁用。

兜底判定：拿不准该用哪个词时，把档位往低定一档——把 inference 写成 direct 属违规，反向降级无害。

## 本仓类别映射

`/mana why` 的派发类别是**本机实际可用**的来源，不是固定清单。本仓/本机（OMP + Pi + herdr，`gh` 可用）默认映射：

| 类别 | 来源与工具 | 最适用的「为什么」 |
| --- | --- | --- |
| source control | `git blame -L`、`git log --follow -p`、`git log --oneline -20`、`git log -1 --format=%B`、`gh pr view --json ...` 逐条读 | 实现时的取舍与评审中写下的 rationale；唯一保证可用的类别（永不缺席，缺席理由只能是「该范围无 commit 历史」） |
| issue tracker | `gh issue view <n> --json ...` 含评论、`gh pr view <n> --comments`、PR 关联的 closing issues | 产品/业务迫使力：需求侧为什么——客户诉求、deadline、竞品压力 |
| long-form docs | 仓库内文档（`docs/`、README、`*.md`）与 session 记忆（`.mana/` 留档、run 后复盘结论） | 变成代码**之前**写下的长篇设计 rationale |
| codebase-memory MCP | 环境可用时单列一类；调 `search_graph`、`trace_path`、`get_code_snippet` 取结构化证据 | 符号间调用关系与归属边界，供锚点扩充与推断链取证 |

将来接入新的证据类别（例如其他 issue tracker、协作平台、观测平台），照 source-playbook 的形状补一份该类别的取数命令与「最适用的为什么」映射，再把类别加入此表——不移植既有平台的 playbook 文件。

## Document the null（缺口纪律）

派发时对本机可用的类别**逐一**建 lane；某类别存在但查不到东西，或该类别在本机不可用，都必须写进最终输出的缺口清单——写明「查了什么、词是什么、范围多大、无命中」或「本机无此类别，未查」。**不许因为「多半不会有」而跳过搜索**：缺口清单是合成时「unknown」定级的直接依据，也是后续补查的工作清单。合成输出里 Sources Consulted 每条 lane 一行——返回空的和被跳过的也各占一行，写明原因。
